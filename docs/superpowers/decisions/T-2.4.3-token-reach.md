# T-2.4.3 follow-up — Session tokens reachable from the content script (F-14 remainder)

Status: **awaiting owner** (loop 9, 2026-11-28). Blocks nothing on the critical path; PR #32 ships without it.
Approve with `APPROVED: <option>`.

## Context

A fresh verifier of PR #32 confirmed the content script no longer *reads* the account session (it watches the
separate `promptizer.signedIn` flag). The tokens still *reach* the content script, though:

- `session-store.ts` writes the session and the flag in one `storage.local.set`, and `storage.onChanged` hands every
  listener the whole `changes` object. The content script has two `local` listeners (`session-store.ts:13`,
  `content/global-enabled.ts:33`), so `promptizer.accountSession.newValue` (access and refresh token) is delivered
  into the page's renderer process on every save or renewal.
- `storage.local` cannot be locked to trusted contexts. Only `storage.session` has `setAccessLevel`, and its default
  (`TRUSTED_CONTEXTS`) already keeps content scripts out.

Content scripts run in the web page's renderer process. Normal page script cannot reach the isolated world, but a
renderer exploit on a hostile page could read anything the content script can read. T-2.4.3 also requires that a
browser restart leaves the user signed in, so the refresh token must persist somewhere.

## Options

**A. Accept, and stop broadcasting tokens. Recommended for MVP.** Keep both tokens in `storage.local`. Write the
flag in its own `set` call, and have the content script listen only for the keys it needs (its handlers ignore other
keys already, but the change still carries the value). Document the residual risk (direct `storage.local` read after
a renderer compromise). Small diff, no behaviour change.

**B. Split the tokens.** Access token in `storage.session` (content scripts locked out). Refresh token stays in
`storage.local`, so restart still keeps the user signed in. Renewal writes only `storage.session` plus the rotated
refresh token. Narrows exposure to the long-lived refresh token, which is the more valuable one, so the gain is
partial. Medium diff in `session-store.ts` / `session-manager.ts` plus tests.

**C. Session-only.** Everything in `storage.session`. Nothing token-bearing is reachable from content scripts, but
every browser restart signs the user out. Fails T-2.4.3 box 1; needs a plan change.

**D. Background worker owns tokens.** Pairs with decision T-6.1.2 option A (worker relay). Content script and popup
never touch tokens, only messages. The refresh token still lives in `storage.local`, so it has the same residual risk as A/B
unless combined with C.

## Consequences

- A: one small PR on top of #32; F-14 closes with a documented residual risk.
- B/D: schedule after Epic 6's write channel lands; revisit with T-7.2.1 (privacy verification).
- C: owner must amend T-2.4.3.
