# T-6.3.1 — Conflict detection for writes from the extension

Status: **awaiting owner** (loop 8, 2026-11-28). Blocks T-6.3.2 (and the conflict half of T-6.2.1). Approve with
`APPROVED: <option>`.

## Context

`PATCH /api/prompts/[id]` (`updatePrompt` in `apps/web/src/lib/server/prompts.ts`) is last-write-wins today. It
updates the `prompt` row (setting `updated_at`), then appends a `prompt_version` row when text changes. The
extension edits from a cached snapshot that may be minutes old, so a blind PATCH could overwrite a newer
dashboard edit. That breaks "the newer server text is never silently overwritten".

## Options

**A. Base-timestamp compare-and-set. Recommended.** Every extension write sends `baseUpdatedAt`, the `updatedAt` it
last saw. The row update becomes `update(...).eq("id", id).eq("updated_at", baseUpdatedAt)`. Zero rows on an
existing prompt means a conflict.
- Refusal: `409 { code: "conflict", message: "This prompt was updated elsewhere.", current: Prompt }`. The current
  server copy travels with the refusal, so the picker can show it and the user can retry from it.
- No migration. `updated_at` already moves on every title, text or pack change. The dashboard keeps sending no
  `baseUpdatedAt` and stays last-write-wins for its own auto-save (it is always editing the freshest copy).
- `packages/shared`: `PromptChanges.baseUpdatedAt?: string`, `ConflictErrorBody` and a `CONFLICT_ERROR_CODE`
  constant. That is where the rule is recorded for both apps.
- Caveat: millisecond timestamps. Two writes in the same millisecond are not distinguished. That's acceptable for
  one user on two surfaces.

**B. Integer `revision` column.** This is the strictest compare-and-set, but it needs a migration and a backfill, and every
write path (dashboard auto-save included) must bump it. More work for the same guarantee in practice.

**C. Text-hash precondition.** The client sends a hash of the text it edited. It catches text conflicts only, misses
title and pack changes, and needs hashing on both sides.

## Consequences

- With A: T-6.3.2 adds the conditional update with tests on the endpoint (stale base → 409 with `current`, fresh
  base → 200, missing base → unchanged behaviour) and on the client (conflict result → "updated elsewhere" UI).
- Under the T-6.1.2 decision (option A there), the worker maps `409 conflict` to the tagged `conflict` result.
