# T-3.0.1 — Prompt & pack data shape

Status: **awaiting owner** (loop 1, 2026-11-27). Approve by adding a line `APPROVED: <option>` below.

## Context

Epic 3 landed on `main` before the plan was tracked. What exists (`supabase/migrations/20261126000000_init_prompts.sql`,
`packages/shared/src/index.ts`):

- `prompt`: id, user_id, title, `category_id` (one per prompt), `model`, `example_usage`, `example_output_*`,
  created_at, updated_at. Text lives in `prompt_version.body` (latest version; saves overwrite it in place).
- `category`: id, user_id, name (1–80), created_at. No `updated_at`. Deleting it sets `prompt.category_id` to null, so
  prompts survive (the Epic 4 business rule already holds).
- `tag` + `prompt_tag`: a many-to-many organizer the product plan defers to "Later".
- Shared contract: `Prompt` exposes `model` and `category`; `PROMPT_TEXT_MAX_LENGTH = 20_000`,
  `PROMPT_TITLE_MAX_LENGTH = 200`. There is no `Pack` type.

The plan asks for prompt fields "id, owner, title, text, timestamps — nothing more", pack fields "id, owner, name,
timestamps", and a decided prompt↔pack relation. Epic 4 expects adding prompts to a pack from both the pack page and
the prompt page, per-pack remove, and "same prompt in multiple packs" behaving per this decision.

## Options

**A. Category is the pack (one pack per prompt).** No migration. Rename `category` to "pack" in the shared contract
(`PackSummary`, `packId`) and UI only. Membership = setting `prompt.category_id`; "add to pack" moves a prompt out of
its previous pack. Pack lacks `updated_at` (rename reorder/staleness uses `created_at` only, or needs a migration
anyway).
- Cheapest; delete-preservation already works.
- Surprising UX: adding a prompt to "Writing" silently removes it from "Email". Epic 4.2's per-pack remove list on a
  prompt page is always 0–1 entries.

**B. Dedicated `pack` + `pack_prompt` (many-to-many). Recommended.** One new migration:
`pack(id, user_id, name, created_at, updated_at)` and `pack_prompt(pack_id, prompt_id, user_id, created_at)` with
composite owner FKs and `on delete cascade` on both sides (deleting a pack drops memberships only). Copy existing
`category_id` assignments into `pack_prompt`, then stop exposing `category`/`tag`/`model`/`example_*` from the shared
`Prompt` contract (columns may stay in the DB until a later clean-up migration). Shared definitions gain `Pack`,
`PackSummary`, `PACK_NAME_MAX_LENGTH = 80`, and `Prompt.packIds`.
- Matches the plan's wording for Epics 4–5 (snapshot = prompts + packs + membership).
- Needs owner approval: agents must not apply DDL to hosted Supabase, so the owner applies the migration.
- List filter `?category=` becomes `?pack=` via a membership join; one more candidate query in the search merge.

**C. Reuse `tag`/`prompt_tag` as packs.** Many-to-many without a migration, but the name "tag" contradicts the plan
("tags: later"), tags have no `updated_at`, and a 40-char name limit; two organizers (category + tag) remain in the
schema with confusing overlap.

## Recommendation

**B.** Also fix the prompt contract to the plan: `Prompt = { id, title, text, packIds, createdAt, updatedAt }`
(owner is implicit in the authenticated API). Keep `PROMPT_TEXT_MAX_LENGTH = 20_000` as the shared text limit.

## Consequences

- Blocks: T-3.0.1 checkboxes, T-3.2.1/T-3.2.3 pack filter re-verification, all of Epic 4, T-5.1.1 onward.
- After approval the next loop builds one task branch `mvp/T-3.0.1-pack-shape` (migration file + shared types +
  API/UI rename from category to pack), then Epic 4 stacks on it.
- The owner must apply the migration to the hosted Supabase project before the Supabase-backed suites can run.
