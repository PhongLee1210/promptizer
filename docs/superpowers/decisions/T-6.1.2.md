# T-6.1.2 prerequisite — How the content script reaches the API for writes

Status: **awaiting owner** (loop 8, 2026-11-28). Blocks T-6.1.2, T-6.2.1 and T-6.2.2. Approve with `APPROVED: <option>`.

## Problem

Saving or editing from the rail starts in the content script, which runs on the host page (chatgpt.com, claude.ai, …).
Its `fetch` is subject to the page origin's CORS. `apps/web/src/proxy.ts` only sends CORS headers when
`Origin === EXTENSION_ORIGIN` (`chrome-extension://<id>`), so a content-script `fetch` to `/api/prompts` is refused.
Today the extension has no background entrypoint. Every API call comes from the popup, which is an extension origin.
The content script also must not hold the access token (Journey D privacy: credentials stay in extension storage).

## Options

**A. Background service worker relays writes. Recommended.** Add `src/entrypoints/background.ts`. The content script
sends `{ kind: "save-prompt", title, text }` or `{ kind: "update-prompt", id, baseUpdatedAt, changes }` through
`browser.runtime.sendMessage`. The worker reads the session through the existing `accountSession`, calls the API with
the existing client pattern (extension origin, so CORS passes), updates the library cache, and returns a tagged result
(`ok` / `conflict` / `retryable` / `unauthenticated` / `invalid`).
- Tokens never enter the page's isolated world. One place owns renew-on-expiry. The picker cache stays consistent
  because the worker writes it.
- Manifest gains a `background.service_worker` but **no new permissions**. The extension-analyze audit should still
  run once.
- Cost: about 1h scaffolding (message types in `packages/shared`, one worker, Puppeteer E2E through the worker
  with request interception on the worker target).

**B. Widen server CORS to any origin for `/api/prompts` with a bearer token.** The content script reads the token from
`browser.storage.local` and calls directly.
- No new entrypoint, but the token sits in every page's content-script world, and any page's origin is allowed to
  call the API with it. This weakens Journey D. Not recommended.

**C. Popup-only writes.** The rail opens the popup (or a new tab) prefilled with the text. No CORS or token issue,
but it breaks the "save from the rail" journey (Journey C) and adds a context switch.

## Consequences

- With A: T-6.1.2 builds the worker plus the rail Save action. T-6.2.1 reuses the same channel. T-6.3.3's three
  honest messages map 1:1 to the tagged result.
- T-6.1.1 needs no new endpoint under any option. `POST /api/prompts` already validates title and text like the
  dashboard, requires a bearer session, and returns the created prompt (201). It is covered by the existing
  Supabase-backed prompt API suite.
